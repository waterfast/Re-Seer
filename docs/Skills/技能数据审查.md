# 技能数据审查（2026-10-06）

## 这份 JSON 是什么

`GameContent/Generated/Server/skills.json` 是技能规则的服务器交换格式样例，由 `SkillDatabaseSO.ToServerJson()` 生成。唯一编辑源是 `Assets/Game Data/SkillDatabase.asset`；Unity UI 直接查这个数据库，并不读取导出的 JSON。现有四条 `demo_*` 是流程示例，不是正式技能库，也不是官方技能数值。

服务器投影省略了名称、描述、图标和表现资源字段，这是合理的边界。运行时剩余 PP 放在 `BattleSkillState`，也不应写回静态技能资料。

## 两个版本字段

- `schemaVersion` 是整份交换文件的结构版本。它在导出类中固定为 `1`。只有字段含义或格式发生不兼容变化时才需要考虑升级；增加技能或调整威力不等于改变格式。目前没有读取器检查这个字段，它只是预留。
- `contentVersion` 是整份技能库的内容发布标识，不是单条技能的版本。它由编辑器手动填写，目前是字符串 `"1"`；校验只要求非空，没有客户端/服务器一致性检查，也没有自动发布机制。修改内容不会自动改变它。

如果最终采用服务器权威结算、客户端只展示技能的方式，不一定需要手工维护一个技能内容版本。如果以后需要热更新、回放复现或多批客户端并存，仍需明确某场战斗使用哪份规则；可以由构建或发布流程生成整包标识/内容哈希。哈希可以识别内容差异，但不能替代格式兼容性判断。

建议：服务器格式尚未确定前，不把手工维护 `contentVersion` 当成正式技能编辑的必需操作。接服务器时再决定是否移除它或将其迁移到发布清单。`schemaVersion` 是否保留，取决于读取器有没有实际兼容性需求。当前只做审查，未删除字段或改变导出接口。

## 比版本字段更实质的缺口

1. **规则尚未接通。** `SkillData` 的效果记录是 `effectId + key/value`；旧 `ReSeer.Combat.Skill` 使用具体 `Effect` 对象。现有具体效果是固定伤害 `DamageEffect`，没有从这份 JSON 建立战斗规则的加载器。JSON 中的解除强化、提升能力、麻痹等不能据此视为已实现。
2. **校验只覆盖基础结构。** `Validate()` 检查 ID、基础数值、效果/参数是否为空和参数名是否重复；没有验证效果是否存在、元素/状态 ID 是否存在、必需参数或参数类型及范围。`chance = "abc"`、未知 `effectId` 等仍可能通过。应在确定支持的效果集合后，为每种效果定义实际参数契约与校验。
3. **数值约定不统一。** 命中率用万分比整数 `10000`，效果概率用字符串 `"0.3"`；倍率、能力等级也是字符串。字符串可以作为编辑/传输形式，但读取时需要明确单位、解析方式及范围，不能依赖效果实现各自猜测。
4. **导出需要手动操作。** 保存数据库不自动重新生成 JSON，也没有检查导出与源资产是否一致。应在构建/发布时统一校验和导出，以免发布旧文件。
5. **示例验证限制了正式内容。** `SkillDataVerification.Run()` 要求记录数必须为四并且特定示例 ID 必须存在。这适合验证当前演示，不适合作为可扩充的正式内容检查；正式校验应与示例行为验证分开。

## 改进顺序

先明确客户端展示、服务器规则的边界和第一批真正支持的效果；再补效果契约、加载与校验以及自动导出；最后按发布需求决定版本策略。单一编辑源、稳定 ID、静态资料与战斗状态分离可以保留。现阶段的问题是未闭合的数据流程，而不能仅凭两个预留字段判断整体架构失败。

本次依据仓库源码和样例做静态审查，未运行 Unity，也未验证服务器结算。
